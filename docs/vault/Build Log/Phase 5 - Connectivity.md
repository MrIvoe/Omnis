| 2026-08-18 | Library scanning | Closed the tracker's "no fingerprint-based track identity" gap — and a real, live bug found while scoping it: `MediaScanner` ids every local track as `local:${file.path}` (confirmed directly in `_scanAndroid`/`_trackFromFile`), so renaming or moving a file gave it a brand-new id on the very next rescan. Since favorites/ratings/play history/playlist membership are all keyed by track id, that meant a rename silently orphaned every bit of a track's history: the old id vanished (its file no longer existed at the old path, so `library_page.dart`'s own "prune tracks whose file is gone" step dropped it), a "new" track appeared with zero history, and nothing ever remapped the old references to the new id. New `lib/core/track_fingerprint.dart`'s `computeFileFingerprint`: hashes a file's size plus its first and last 64 KB (not the whole file — a deliberate cost tradeoff so rescanning a library of large lossless FLACs doesn't get noticeably slower for a signal that doesn't need every byte; a rename never touches file content, so a large sample from each end already distinguishes it from a same-sized-but-different file). New `lib/core/track_fingerprint_store.dart`'s `TrackFingerprintStore`: persists an id-to-fingerprint map (the same load/save-JSON-file, caller-owns-the-map shape `PlaylistStore`/`CustomMoodStore` already established) — has to exist because a file that's already disappeared can't be re-read to fingerprint it retroactively, so every genuinely new local track's fingerprint is recorded the moment it's first added, not just when a rename is later suspected. New `lib/core/rename_reconciliation.dart`'s pure `reconcileRenamedTracks`: matches a scan's unrecognized "new" files against the current scan's newly-missing files by fingerprint; a match keeps the OLD track's id/dateAdded (every id-keyed reference stays valid) but takes every other field from the fresh scan (the file may have been re-tagged as part of the same move); each missing track matches at most one candidate; a missing track with no recorded fingerprint (added before this feature existed, or non-local) can't be recognized as a rename source and is treated as a real deletion, same as always; a real deletion's now-stale fingerprint entry is pruned so the store doesn't grow unboundedly over a library's life. Deliberately a pure, dependency-injected function (`computeFingerprint` passed in, not called directly) rather than logic embedded in `LibraryPage._pickAndAdd` itself — this codebase has a documented, known gap that `library_page.dart` has no widget-test file at all (`flutter test` can't safely construct a real `AudioEngine`), so the actual matching/pruning logic needed to live somewhere genuinely testable; `_pickAndAdd`'s own `_reconcileRenamedTracks` is now a thin loads-the-store/delegates/saves-the-store wrapper, verified only via `flutter analyze` per that same established exception. The same fix was also applied to `lib/core/main_core.dart`'s `_mergeScanIntoLibrary` — shared by the desktop filesystem watcher's `onSettled` callback, the scheduled background scan, and the command palette's "Scan library" action — since its own doc comment already promised it "mirrors `library_page.dart`'s own `_pickAndAdd` merge exactly," and leaving it unfixed would have meant a rename only survived when the user happened to rescan through the Library page's own button, not through any of the other three real rescan triggers. 30 new tests: 6 in `test/rename_reconciliation_test.dart` (a real rename match preserves id/dateAdded while taking fresh fields; no match is a real delete+add with pruning; a missing track with no recorded fingerprint can never be recognized; each missing track matches at most one candidate; fingerprints get recorded even with nothing to reconcile against; unrelated existing entries are left untouched), 8 in `test/track_fingerprint_test.dart` (same content/different path hashes identically; different content hashes differently; a file larger than the 64 KB sample window exercises both the head and tail read — including a tail-only content change actually changing the result; a nonexistent or empty file returns `null`, never throws; a `TrackFingerprintStore` save/load round-trip and corrupt-file recovery, the same `_FakePathProvider` pattern `test/library_store_test.dart` already established). Full suite: 1637 passing (was 1623), `flutter analyze` clean. Main-repo-only change, no cross-repo bump needed — deliberately kept the fingerprint out of `BaseTrack`'s own schema (a separate side-store instead) specifically to avoid one. Item 5 promoted from 🟡 to ✅ — every gap this tracker had named for it (incremental rescan, the desktop watcher, scheduled scans, and now rename/move identity) is closed. |
